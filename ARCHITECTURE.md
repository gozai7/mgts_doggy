# Архитектура и принятые решения

## Аудит исходного проекта

В предоставленном ZIP уже существовал ROS 2 Jazzy/Docker workflow: `sim/` генерирует сцены
и bag, `solver/solve.py` строит 2D-карту через slam_toolbox/Karto и локализует через AMCL,
`solver/refine.py` и связанные скрипты выполняют офлайн-уточнение. Есть направленный Karto-патч,
экспорт графа, оценки траекторий, тестовые сценарии и сохранённые сравнения.
GLIM, RKO-LIO и выбранного 3D localizer там не было. Записанные legacy-метрики не являются
проверкой новых стеков. Успешная сборка legacy в этой среде также не подтверждалась.

Новая общая инфраструктура размещена в `competition/`; старые solver/sim не переписаны.
Общими остались Docker/Compose/Make, разделение input/result, конфигурации, TUM/CSV и офлайн-подход.
Прямое встраивание 3D LIO в старый 2D solver смешало бы несовместимые контракты; поэтому
новая точка входа `python -m competition.runner` отделена, а прежняя доступна через `.legacy`.

## Поток данных

1. Bag Doctor читает metadata и ограниченное число сообщений. Тяжёлые облака семплируются.
2. Input Adapter проверяет структуру, единицы и калибровку. Создаёт новый SI bag;
   исправленные header timestamps становятся временем записи. Сортировка выполняется на диске.
3. Выбранный алгоритм обрабатывает первый нормализованный bag и строит 3D-карту.
4. Экспорт переводит позы физического сенсора в base и сохраняет метаданные frame.
5. Localizer загружает оптимизированную карту, затем получает второй bag пошагово.
   Следующий скан передаётся после результата регистрации текущего, по точному stamp_ns.
6. Occupancy использует отдельные сканы и финальные позы LiDAR. Ближайший endpoint в угловом
   секторе ограничивает raycasting; ненаблюдавшиеся клетки остаются неизвестными.
7. Evaluation сохраняет доступные метрики. Недоступные поля имеют null.

## Разница A/B

Fast-LIO запускает форк Fast-LIO2 из демо с прямым чтением rosbag2 на ROS 2 Jazzy.
В проходе A он обрабатывает нормализованный PointCloud2 и IMU в порядке времени,
передаёт калибровку `T_imu_lidar` в фильтр и экспортирует инкрементальную карту с вертикалью
по гравитации. Поза IMU преобразуется в base через калибровку `T_base_imu`.
Облака на конец скана сохраняются в физической системе LiDAR для 2D-экспорта.
В проходе B используются общий автоматический поиск начальной позы и `lidar_localization_ros2`.

GLIM обрабатывает bag через `glim_rosbag`; CPU/GPU выбирают собственные конфигурации модулей.
После штатного final save добавлен экспорт глобально исправленных точек в binary PCD.
Исходные `odom_lidar.txt` и `traj_lidar.txt` сохраняются в dump. Расчётный state GLIM связан
с IMU, поэтому для общего контракта используются именно экспортированные LiDAR-позы и измеренный
`T_base_lidar`. Патч не меняет математическое ядро.

RKO frontend использует форк, закреплённый как submodule в выбранном `lidar_slam`.
Он напрямую записывает deskewed PointCloud2 и одометрию base в rosbag2 Writer.
Это устраняет зависимость полноты offline-передачи от скорости DDS recorder; ROS-публикации
upstream сохранены. Затем `graph_slam_offline_runner` обрабатывает эти пары, формирует
ключевые кадры, проверяет геометрические кандидаты на петлю и оптимизирует граф.
Dense-коррекция upstream переносит исправления графа на все позы и отдельные сканы.
Экспортируются `trajectory_optimized_dense.tum` и `map_dense_optimized.pcd`.

В начальном профиле RKO descriptor-поиск отключён: используются пространственные кандидаты,
минимальная длина пути, overlap и ограничения геометрической коррекции. Это снижает область
поиска, но может пропустить петлю при большом дрейфе. Ложные петли всё равно возможны.
Никаких искусственно заданных loop edges нет.

## TF и предсказание

Из исходного bag не копируются динамические map/odom TF. Канонический `/tf_static` содержит
только измеренные base→lidar и base→imu. Frames должны называться различно, даже при identity-mount.
Для локализации с кинематикой replay публикует odom→base, localizer — map→odom.
Без кинематики localizer публикует свой map→base. GLIM живёт в отдельном процессе/этапе.
Нельзя одновременно запускать второй broadcaster для той же пары frames.

При режиме `kinematic` входной Odometry обязан уже описывать физический base в SI.
Автоматического переноса одометрии другого сенсора на base или слияния ног+IMU нет.
Режимы предсказания взаимоисключающие. IMU lever arm и динамика обрабатываются upstream;
адаптер только переводит единицы и задаёт измеренные extrinsics.

## Deskew и occupancy

При point_time отключённом GLIM получает global shutter, RKO/KISS deskew=false,
localizer continuous-time deskew=false. Это осознанный режим с риском искажений на поворотах.
Для GLIM occupancy интерполирует финальные LiDAR-позы для каждого raw point time.
Для RKO используются уже deskewed сканы и соответствующие dense optimized poses.
Интерполяция запрещена вне траектории и через gap больше `max_pose_gap_s`.

Raster-экспорт является приближённой 2D-проекцией: начало лучей берётся в опорной позе скана,
даже если endpoints компенсированы по времени точки. Это не полноценная 3D-модель видимости.
Height фильтр предполагает один известный уровень пола в map. Лестницы/несколько этажей,
динамические люди и стекло не решены. Клетки со слабым единичным попаданием остаются unknown;
требование повторных попаданий консервативно и не является моделью вероятностного удаления динамики.

## Воспроизводимость

Исходники основных стеков включены в ZIP и закреплены полным SHA. Патчи выделены в `patches/`.
Зависимости FetchContent имеют закреплённые версии, optional viewer — SHA submodules.
ROS base image закреплён digest. APT не зафиксирован snapshot-репозиторием: побитовая
воспроизводимость образа не обещается. Сборка сохраняет `build-apt-versions.txt` и
`build-python-versions.txt`; до финала следует сохранить готовый image через `docker save`.

Manifest нормализованного bag проверяет конфигурацию и size/mtime исходных файлов. Это
быстрая проверка cache identity, а не полный криптографический хеш сенсорных данных.
Результаты одного запуска не перезаписываются автоматически. Для эксперимента выбирают новый output.
