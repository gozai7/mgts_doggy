## Запуск

Требуется собранный `mgts-competition-glim:gpu`. На тестовом ноутбуке выполните `export DOCKER_CONTEXT=mgts`.

```bash
make go2-rviz PHASE=localization      # исходные измерения B в RViz, по кругу
make go2-map                         # GLIM на A
make go2-locate                      # исходный холодный поиск и NDT на карте GLIM
make go2-live RUN_NAME=demo-01        # GLIM на A и B, затем локализация B на карте A при 1×
make go2-result RUN_NAME=demo-01      # RViz с записанным результатом demo-01
```

Для нового живого прогона выберите свободное имя. Без RUN_NAME оно формируется по времени. В исходном эксперименте с GLIM v2 поиск старта для NDT завершился ошибкой связывания последовательных сканов. Для итогового прогона используйте `go2-live`. На уже созданном неуспешном checkpoint раннер сохраняет диагностику и отказывается перезаписывать каталог.

## Что входит в замер

GLIM читает сырые 3D-сканы `/utlidar/cloud` и IMU `/utlidar/imu`. Между соседними позами IMU в графе GLIM добавляется относительное движение корпуса из `/utlidar/robot_odom` с учётом рычага IMU. Вес фактора задают `kinematic_translation_sigma_m` и `kinematic_rotation_sigma_rad`. Это параметры оптимизации. Поворот IMU оценён по сопоставлению гироскопа и направления тяжести с одометрией A. Для плеча IMU принято положение центра лидара. Медианная норма ускорения составляет 9,71 м/с² на A и 9,80 м/с² на B. Во всех сообщениях IMU три матрицы ковариации заполнены нулями. По 2 477 соседним отсчётам в 20 спокойных полусекундных окнах A оценены эффективные плотности белого шума. Для каждой оси взята робастная оценка стандартного отклонения разностей через MAD, умноженная на √(Δt/2). Медианы по трём осям составили 0,00737 (м/с²)/√Гц и 0,000329 (рад/с)/√Гц. Для случайного дрейфа смещения оставлены параметры GLIM. Это оценка на коротких участках работающего робота.

По сырым сообщениям A/B максимальное `time` точки коррелирует с интервалом до **следующего** скана (0,924 / 0,938). Оно записано как float32 в секундах относительно начала скана. Перед прибавлением к метке Unix смещение переводится в float64. Та же конвенция времени описана в [SDK Unitree](https://github.com/unitreerobotics/unilidar_sdk2/blob/main/unitree_lidar_sdk/include/unitree_lidar_utilities.h#L50-L67).

В `go2-live` позы A берутся из оптимизированного дампа GLIM. По повторным наблюдениям вертикальных плоскостей уточняются горизонтальные смещения и курс A. Каждый пятый скан отложен для проверки. При недостаточном перекрытии или ухудшении проверки сохраняются позы GLIM. Каждый сырой луч A переносится в карту по уточнённой позе на время этого луча, после чего облако прореживается вокселем 5,5 см. Разреженная штатная карта GLIM остаётся в каталоге дампа. Единый жёсткий перенос совмещает первую позу A с локальной системой одометрии A. Глобальный поиск на B сопоставляет короткую последовательность сканов с картой, используя только относительное движение из одометрии B. После разрешения конкурирующих гипотез каждый сырой скан B с доступной одометрией получает позу. Лучи приводятся ко времени начала скана по уже полученной одометрии корпуса. Лидарная поправка использует расстояния до локальных плоскостей карты вдоль наблюдаемых направлений, остальные компоненты задаёт одометрия. Чётные и нечётные точки разделены между расчётом поправки и её проверкой. При отклонении поправки публикуется прогноз с последним принятым преобразованием между одометрией и картой.

В `results/<имя>/` сохраняются `timing.json`, `initialization.json`, `map.pcd`, `trajectory.tum`, `tracking.csv` и `result_bag/`. Для каждой позы источник `lidar` или `odometry` записан в топик `/competition/result/source`. До обнаружения старта абсолютные позы отсутствуют. Задержка измеряется от записанного момента поступления облака до получения ROS-сообщения с позой. Стенд — Ryzen 5 5600H, RTX 3060 Laptop. GLIM использует GPU для построения карты. Онлайн-трекер B работает на CPU. В RViz голубым показан проход A, оранжевым — онлайн-локализация B, фиолетовым — отдельный проход GLIM по записи B. Для фиолетовой линии используется одна жёсткая привязка к A по автоматически найденной стартовой позе. Это ретроспективный результат.

## Результат на официальных A и B

На 43 общих участках длинной стены медиана поперечного расхождения между двумя проходами A уменьшилась с 1,90 м до 12,9 см после усиления веса относительного поворота в GLIM. После сопоставления повторно наблюдаемых плоскостей она составила 2,72 см, p90 — 4,65 см, максимум — 28,87 см. При замене отложенных сканов медиана составила 2,77 см. Вне длинной стены встречаются участки с ухудшением. Эти величины описывают повторяемость поверхности в A. Абсолютная ошибка позы на официальных записях неизвестна.

В прогоне `official-glim-refined` карта содержит 130 209 точек, полный маршрут GLIM A — 1 673 позы, независимый GLIM B — 1 510. При воспроизведении B с исходной скоростью автоматический поиск опубликовал первую позу через 49,65 с. До привязки прошло 690 сканов. Из последующих 836 поз 597 получили лидарную коррекцию и 239 опирались на кинематический прогноз. Задержка p95 составила 8,99 мс. Все 835 ответов с известным следующим дедлайном успели до следующего облака. Оранжевая линия в RViz начинается с первой опубликованной онлайн-позы, фиолетовая показывает весь восстановленный ретроспективно маршрут B.

В RViz выбран `Move Camera`. Над картой удерживайте левую кнопку мыши для поворота, среднюю для сдвига. Колесо меняет масштаб.
