# Runbook: подготовка и финал

## До финала

1. На ноутбуке собрать CPU-образ выбранной ветки (`make build`) и GLIM GPU при необходимости.
   Выполнить `make test-unit` и настоящий `make smoke-test`. При любом FAIL сохранить полный build/runtime log.
2. Прогнать короткий реальный bag робота, затем оба полных прохода. Измерить время, RAM/VRAM,
   coverage и стабильность. На этом основании выбрать основной профиль и резервный.
3. Проверить ручную initial pose, просмотр PCD/PGM и вход без per-point time.
4. Сделать несколько отдельных fault cases: ±20/50 ms IMU, 25% точек, gap 1 s.
   Не менять несколько факторов одновременно, пока причина не локализована.
5. Сохранить images через `docker save`, исходные ZIP, lock и калибровки. Испытать запуск
   без сети. Убедиться, что хватает диска на исходный, нормализованный и промежуточный bag.

Пример сохранения уже успешно собранного CPU image:

```bash
docker save mgts-competition-fast-lio:cpu -o competition-fast-lio-image.tar
```

## Получили данные: первые 5–10 минут как рабочий ориентир

1. Сохранить оригиналы и metadata; уточнить официальный формат сдачи, sensor mounts,
   единицы IMU/XYZ, значение cloud stamp, поле point time и наличие неподвижной фазы.
2. `make doctor`, `make doctor PHASE=localization`. Проверить type/topics, rates/gaps,
   NaN, time candidates, перекрытие, TF и kin odom. Ошибки структуры устранять до SLAM.
3. Заполнить dataset.yaml измеренными данными. `auto` допустим лишь при одном topic нужного типа.
4. `make prepare`; проверить сгенерированные конфиги. Для закрытой карты оставить
   `initial_pose: null` и `manual_initial_pose: false`. Найденная поза появится в `localization/initialization.json`.

## Маппинг и выбор результата

```bash
make baseline
make mapping
```

KISS-ICP нужен для диагностики; он не заменяет глобальную карту. При проблемах LIO
сравнить движение и временные шкалы с KISS, проверить IMU/extrinsics и неподвижную фазу.
Если оба метода расходятся, проверить LiDAR/геометрию; никакой вывод не считать однозначным диагнозом.

Проверить `mapping/complete.json`, coverage, логи initialization/loop closure, карту и trajectory.
Осмотреть повороты, пересечения коридоров, высоту пола, двойные стены и явные скачки.
Нельзя выбирать карту только по красивой замкнутости. Вторая реализация запускается в своём
распакованном проекте и отдельном output. Полные времена на неизвестном bag не гарантируются.

## Второй проход, occupancy и сдача

1. Для автоматического поиска позы B оставить `initial_pose: null` и
   `manual_initial_pose: false`. При известном старте можно указать позу base в системе map.
2. `make localization`; проверить accepted fraction, длинные серии отказов, fitness и ошибочные
   совпадения похожих коридоров. Не выдавать разрывы за непрерывную подтверждённую траекторию.
3. Установить `occupancy.floor_z_m` в map и диапазон высоты препятствий. `make occupancy`.
   Проверить неизвестные области, проходы и занятость стен, затем `make evaluate`.
4. Проверить TUM/CSV: timestamp seconds, xyz metres, qxyzw, pose base in map.
   Сопоставить с форматом организаторов; сохранить конвертацию отдельным файлом, не испортить оригиналы.
5. Сдать нужные map.pcd, map.yaml+map.pgm, траектории и пояснение методов/ограничений.
   Для презентации снять RViz и сохранить реальные метрики, версии, конфигурацию и logs.

## Если этап упал

`failed.json` и логи остаются в результате. Завершённый mapping не удаляется.
После устранения причины перенесите только неуспешный каталог этапа в отдельное имя
и повторите соответствующий make-target; при изменении calibration/mapping-параметров создайте новый output.
Нормализатор `.partial` сохраняет для диагностики: перед повтором уберите именно этот частичный
каталог или используйте новый output. Не удаляйте автоматически исходные bag.

Изменение только initial pose/localizer не инвалидирует mapping. Изменение только floor/occupancy
не требует нового SLAM, но уже успешный occupancy-export с другими настройками не перезаписывается.
`make run-all` повторно использует подходящие успешные checkpoints.

При дефиците времени сохраняйте уже проверенные результаты. Отсутствие петли предпочтительнее
ручного ложного замыкания. Не называйте endpoint distance или agreement двух методов ATE.
